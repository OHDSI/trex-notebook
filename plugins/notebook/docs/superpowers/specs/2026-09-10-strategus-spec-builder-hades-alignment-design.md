# Design: align the Strategus spec builders with the pinned HADES runtime

**Date:** 2026-09-10
**Status:** proposed — awaiting approval
**Base branch:** `develop`
**Plugin:** `plugins/notebook` (`@trex/notebook`)

## Problem

`plugins/notebook` ships two standalone Strategus analysis-specification builders:

- `src/kernels/webr/StrategusSpecBuilder.R` — evaluated into WebR's global environment
- `src/kernels/pyodide/strategus_spec_builder.py` — executed into the Pyodide worker

Both inline HADES defaults by hand, because neither kernel installs the real HADES
packages: `WebRKernel.ts` shims `library()`, `require()`, `::` and `:::` for a fixed list
(`Strategus`, `CohortMethod`, `FeatureExtraction`, `Cyclops`, `PatientLevelPrediction`, …)
so `Strategus::createCohortMethodModuleSpecifications(...)` resolves to a function sourced
from the builder rather than a package. The Python side needs no shim — the module is
dependency-free.

**Consequence: nothing validates what the builders emit.** A notebook author gets no error
at authoring time. The spec they generate is only exercised later, when it is executed by
the Data2Evidence `strategus_plugin` Prefect flow against the real HADES packages pinned in
`plugins/flows/hades/renv.lock` (repo: `OHDSI/Data2Evidence`).

Today the builders emit objects that those packages reject. A generated CohortMethod spec
fails during Strategus' settings validation before any cohort is built; the failures are
opaque (a bare `java.lang.NullPointerException` from a Java JAR, or
`Expecting a single value: [extent=0]` from Cyclops three layers below the cause).

The underlying defect has one shape, repeated: **an object is built from a constructor's
argument list rather than from the object that constructor actually returns.** Argument
names, field names, and field *sets* all diverge.

## Goal

A specification generated by either notebook kernel executes in the Prefect Strategus flow
without hand-patching, for the CohortMethod and PatientLevelPrediction module surfaces.

## Non-goals

- No change to the kernels (`WebRKernel.ts`, `PyodideKernel.ts`, `pyodide-worker.ts`), the
  shim, the Vue components, or the build.
- No change to `renv.lock` or the Prefect flow in `OHDSI/Data2Evidence`.
- No CI changes (see *Testing*).
- No SelfControlledCaseSeries, Characterization, CohortGenerator or TreatmentPatterns work
  (see *Out of scope*).

## Method: ground truth from the installed packages

Every field set in this design was read from the **installed** package in the running
`alp-dataflow-gen-worker` container, not from a signature, a doc site, or a comment:

```bash
docker exec alp-dataflow-gen-worker bash -c \
  'cd /var/lib/d2e-flows/hades-flow/baked && \
   export LD_LIBRARY_PATH=$(find .pixi/envs/default -name libjvm.so|head -1|xargs dirname):$LD_LIBRARY_PATH && \
   .pixi/envs/default/bin/Rscript -e "cat(names(<pkg>::<constructor>()), sep=\",\")" 2>/dev/null'
```

`LD_LIBRARY_PATH` is required or rJava fails before printing. **Read the OBJECT, not the
signature** — `names(<constructor>(...))`, never `names(formals(...))`. Three traps:

- **Argument names are not field names.** `FeatureExtraction::createCovariateSettings` takes
  `useDemographicsGender` but stores `DemographicsGender` — it strips the prefix internally.
- **A field whose value is empty is dropped from the object.** In R, assigning `NULL` (which
  is what a `c()` default evaluates to) into a list removes the element. So the object is
  routinely *smaller* than the signature, and the difference is not noise — it is the
  contract. Measured on CohortMethod 5.5.2:

  | constructor | formals | object |
  |---|---|---|
  | `createMatchOnPsArgs` | 5 | **4** (`stratificationColumns` absent) |
  | `createStratifyByPsArgs` | 3 | **2** (`stratificationColumns` absent) |
  | `createComputeCovariateBalanceArgs` | 3 | **1** (only `maxCohortSize`) |
  | `createFitOutcomeModelArgs` | 11 | **7** |
  | `createCmDiagnosticThresholds` | 6 | **5** (`attritionFractionThreshold` absent) |
  | `createCreatePsArgs` | 8 | **6** |
  | `createCmAnalysis` | 16 | **4** (every `NULL` slot absent) |

  Supplying a value brings the field back: `createMatchOnPsArgs(stratificationColumns = c("a"))`
  yields 5.
- **The published docs site is ahead of the release.** `ohdsi.github.io/PatientLevelPrediction`
  is built from `main` and lists `createOutcomeLimitedSplitSettings`, which no released tag
  exports. Verify against the installed package, not the site.

Pinned versions (from `renv.lock`, confirmed against the worker): CohortMethod
**5.5.2-0.0.1**, FeatureExtraction **3.11.0**, Cyclops **3.6.0**, Strategus **1.4.0**,
PatientLevelPrediction **6.5.0** (confirmed installed).

## Change set A — Strategus object classes and list shapes

Strategus reads the emitted JSON by S3 class and by JSON type. Both are currently wrong.

| Object | Builder emits | Strategus expects |
|---|---|---|
| every `*Args` object (9 of them) | `"GetDbCohortMethodDataArgs"`, `"CreatePsArgs"`, … | `"args"` |
| `cmAnalysisList` element | `"CmAnalysis"` | `"cmAnalysis"` |
| `outcomes` element | `"Outcome"` | `"outcome"` |
| `targetComparatorOutcomesList` element | `"TargetComparatorOutcomes"` | `"targetComparatorOutcomes"` |
| module specifications | `c("ModuleSpecifications", "<Name>Specifications")` | specific class first |

Unchanged (already correct): `prior` → `"cyclopsPrior"`, `control` → `"cyclopsControl"`,
`covariateSettings` → `"covariateSettings"`, `cmDiagnosticThresholds` →
`"CmDiagnosticThresholds"` (capitalised *is* correct for this one).

**List shape.** The serializer renders a *named* R list as a JSON object and an *unnamed*
list as an array. `cmAnalysisList`, `targetComparatorOutcomesList` and `outcomes` must be
arrays, so they must be assembled unnamed (`unname()`), or a generated spec yields
`"cmAnalysisList": { "cmAnalysis1": {...} }` where Strategus requires `[ {...} ]`.

## Change set C — FeatureExtraction 3.11.0 covariate settings

Two defects in the private default helpers:

1. **Field names carry the `use` prefix.** `useDemographicsGender` must be
   `DemographicsGender`. `createCovariateSettings()` already strips it correctly
   (`covariateSettings[[sub("use", "", name)]]`); the private helpers bypass that logic with
   literal lists, and `createDefaultCovariateSettings()` is built on them — so every spec
   generated through the default path is malformed.

2. **Empty fields are deleted.** In R, `settings$x <- c()` assigns `NULL`, which *removes*
   the list element. `createDefaultCovariateSettings()` does exactly this for
   `includedCovariateConceptIds`, `excludedCovariateConceptIds` and `includedCovariateIds`,
   so three required fields vanish. FeatureExtraction itself keeps them as zero-length
   vectors serialising to `[]`. Python is unaffected — dicts do not drop keys.

The **11 always-present non-flag fields** must appear regardless of which analyses are
enabled: `temporal`, `temporalSequence`, `longTermStartDays`, `mediumTermStartDays`,
`shortTermStartDays`, `endDays`, `includedCovariateConceptIds`, `addDescendantsToInclude`,
`excludedCovariateConceptIds`, `addDescendantsToExclude`, `includedCovariateIds`.

FALSE analysis flags are **legitimately absent** — real `createCovariateSettings()` emits
only enabled analyses plus those 11. Omitting FALSE flags is correct and must not be
"fixed".

The temporal helper additionally emits two flags that FeatureExtraction 3.11.0 does not
accept at all: `useVisitConceptCountStart` and `useVisitConceptCountOverlap` are rejected as
*unused arguments*; the package offers only the single `useVisitConceptCount`. Its
`attr(,"fun")` is also `getDbCovariateData`, the public entry point, where the package names
the worker `getDbDefaultCovariateData`.

## Change set D — Cyclops 3.6.0 control object

`createControl()` emits **15 fields**; `Cyclops::createControl()` has **23**. Missing:
`gridSteps`, `minCVData`, `useKKTSwindle`, `tuneSwindle`, `initialBound`, `maxBoundCount`,
`algorithm`, `doItAll`, `syncCV`. It also emits `cvType`, which is a *constructor argument*
of `createControl()` and not a field of the object.

Cyclops requires the complete object: an incomplete control makes cross-validation collapse
with `Expecting a single value: [extent=0]` inside `CohortMethod::createPs()`. Bisection
showed no single missing field is responsible — the whole set is needed. `createPrior()` is
already correct at 7/7 fields and must not be touched.

## Change set E — PatientLevelPrediction 6.5.0

**The flow runs 6.5.0.** Confirmed first-hand in the worker, not assumed. A bump to 6.6.0 is
proposed in `OHDSI/Data2Evidence` PR #3317 but has not merged, and the flow-hades image has
not been rebuilt — so 6.5.0 is the contract today, consistent with taking the flow as
baseline.

Authoritative object field sets (PLP 6.5.0):

```
modelDesign               targetId, outcomeId, restrictPlpDataSettings, covariateSettings,
                          populationSettings, sampleSettings, featureEngineeringSettings,
                          preprocessSettings, modelSettings, splitSettings, executeSettings
executeSettings           runSplitData, runSampleData, runFeatureEngineering,
                          runPreprocessData, runModelDevelopment, runCovariateSummary
restrictPlpDataSettings   studyStartDate, studyEndDate, firstExposureOnly, washoutPeriod,
                          sampleSize
populationSettings        binary, includeAllOutcomes, firstExposureOnly, washoutPeriod,
                          removeSubjectsWithPriorOutcome, priorOutcomeLookback,
                          requireTimeAtRisk, minTimeAtRisk, riskWindowStart, startAnchor,
                          riskWindowEnd, endAnchor, restrictTarToCohortEnd
preprocessSettings        minFraction, normalize, removeRedundancy
splitSettings             test, train, seed, nfold
modelSettings             fitFunction, param
```

Required changes:

1. `createModelDesign` emits `runCovariateSummary` as a top-level field. 6.5.0 accepts it as
   an *argument* but stores it inside **`executeSettings`**, which the builder does not emit.
   Emit `executeSettings` with the six fields above; drop the top-level key.
2. `createModelDesign` emits **`hyperparameterSettings`**, which does not exist in 6.5.0 —
   no such argument, and no such symbol anywhere in the 6.5.0 namespace. Remove it, and
   deprecate `createHyperparameterSettings` and `setRidgeRegression`, which 6.5.0 also does
   not export.
3. `createPatientLevelPredictionModuleSpecifications` emits `skipDiagnostics`, which has no
   counterpart. Remove it.
4. `splitSettings` must not carry `type` — a constructor argument, not an object field.

The remaining PLP builders are unchecked and get a verification pass in the same task.
`createStudyPopulationSettings` is already verified as a 13/13 match.

**If PR #3317 later merges and the image is rebuilt**, 6.6.0 restores
`hyperparameterSettings`, `createHyperparameterSettings` and `setRidgeRegression`. The
deprecation guards added here must then be revisited rather than silently left in place.

## Policies

**Deprecated arguments stay in the signature and raise.** Removed/renamed arguments are kept
as parameters that `stop()` (R) or raise `TypeError` (Python) with a message naming the
version and the replacement. Rationale: the notebook author finds out in milliseconds
instead of via a failed flow run minutes later — the exact failure mode this feature exists
to remove. They must stay in their **original positional slot**, so a legacy positional call
lands on the guard rather than silently rebinding to whatever live parameter now occupies
that position.

**Default values are not aligned.** Where a builder's inlined default differs from the
package's (`modelType = "cox"` vs `"logistic"`, `washoutPeriod = 365` vs `0`,
`numberOfStrata = 10` vs `5`, `generalizabilitySdmThreshold = 999` vs `1`, `trimFraction`
`NULL` vs `0.05`, and the `createGetDbCohortMethodDataArgs` exposure defaults), the builder
keeps its own value. The builders write every key explicitly, so a default never reaches
Strategus as an absence and therefore never causes incompatibility; aligning them would
silently change study semantics — flipping outcome models from Cox to logistic, dropping a
365-day washout. Only *names* and *field sets* change. Two tests pin this so it is not
"tidied up" later.

## Testing

Test-first, in `plugins/notebook/tests/`, following the emitted-key-set pattern: for each
builder assert the emitted key set equals the pinned package's set **exactly** (catching both
leftover removals and missed additions), that each deprecated argument raises with a message
naming the version, and that key *order* matches across kernels.

- R: `tests/StrategusSpecBuilder-*.test.R` — plain Rscript, `check()` helper, non-zero exit.
- Python: `tests/strategus_spec_builder_*.test.py` — same structure, stdlib only.
- Wired as `test:r` / `test:py` scripts in `plugins/notebook/package.json`.

Expected key sets are hardcoded from the pinned versions, so the suites need no HADES
packages and run offline. Raw `names(<constructor>(...))` output is committed alongside as
evidence, so the provenance claim is checkable rather than asserted.

**Accepted gap: these suites are not wired into CI.** `notebook-plugin.yml` runs only
`npm run typecheck` and `npx vitest run`, and vitest's `include` is
`tests/**/*.test.{ts,tsx}` — so `.test.R` and `.test.py` are neither collected by vitest nor
executed by any workflow, and no CI job installs R or Python (the WebR/Pyodide unit tests
mock those runtimes rather than running them). Wiring them in would mean new CI
infrastructure, mirroring how `function-plugins.yml` introduced `deno test`. That was
considered and **deliberately declined** for this change: the tests run locally and on
demand, but they will not gate a pull request. The drift they guard against therefore remains
detectable only by someone choosing to run them.

## Resolved: emit exactly what the package's object contains

The builders currently emit every key unconditionally. The packages do not: a field whose
value is empty is **absent** from the real object. The rule is therefore simply *mirror the
object* — emit a field when the package would, omit it when the package would, and never
invent one.

This also settles a question the covariate work raised. `CovariateDefaults.ts` in
`plugins/strategus` enables all 38 analysis flags, a superset of FeatureExtraction's default
set, and three flags I suspected did not exist — `DemographicsIndexYearMonth`,
`VisitCountLongTerm`, `VisitCountShortTerm` — were checked and **do exist and are accepted**
in 3.11.0. The enabled-analysis set is a house choice, not a defect, and is left alone.

Note `FeatureExtraction`'s covariateSettings object is the exception that proves the rule:
it *keeps* `includedCovariateConceptIds`, `excludedCovariateConceptIds` and
`includedCovariateIds` as zero-length vectors serialising to `[]`. So "mirror the object"
means checking each object, not applying a blanket omit-when-empty rule.

## The other implementation also diverges — out of scope, tracked

`plugins/strategus/src/services/` is a second, independent spec builder in TypeScript
(`SpecSerializer.ts`, ~1572 lines, plus `CovariateDefaults`, `PlpModelDefaults`,
`DefaultsFactory`, `SpecDeserializer`, `StudyTypePresets`, `mergeSettings`). Both it and the
notebook builders feed the same Prefect flow.

It is markedly more current — its Cyclops control is complete and correctly ordered, its
module classes are specific-first, it emits `executeSettings`, and it omits
`hyperparameterSettings` — which independently corroborates this design's conclusions. But it
is **not** a clean reference to copy: verified against the installed packages, it diverges in
five places.

| Surface | Divergence |
|---|---|
| `truncateIptwArgs` | emits `upperLimit`/`lowerLimit`; the real object's only field is `maxWeight` |
| `trimByPsArgs` | emits `{}`; the real object needs `trimFraction` |
| PLP `executeSettings` | adds `runCalibration`/`calibrationBins`, absent in 6.5.0 |
| PLP `splitSettings` | adds `type`, a constructor argument rather than an object field |
| `cmAnalysisList` | extraneous `createStudyPopulationArgs` sibling key |

Plus one suspected and not independently instrumented: the Characterization module's
`defaultCovariateSettings` appears to use `use`-prefixed keys.

These live in a different plugin and are **out of scope here**, recorded so they are not
lost. The consequence for this design is that the packages — not the TypeScript — are the
contract; the TypeScript is a useful cross-check, nothing more.

## Risks

- Verified end-to-end against one CohortMethod study shape. A spec exercising `trimByPs` or
  `stratifyByPs` takes paths no integration run here covers; the unit suites are the only
  guard there.
- Change set E is unverifiable against the flow until PR #3317 lands and the image is rebuilt.
- Both spec-builder files are loaded via Vite's `?raw` import and evaluated wholesale at
  kernel-connect time, so any change takes effect only after a fresh kernel connect — not on
  hot edit. Manual verification must reconnect the kernel.
- The builders are ~2400 (R) and ~2500 (Python) lines and must stay in lockstep. Cross-kernel
  parity is asserted by the tests, but nothing structurally prevents them diverging.

## Out of scope, with reasons

- **SelfControlledCaseSeries** — same `*Args` class-name issue is likely present, but
  `createSelfControlledCaseSeriesModuleSpecifications` wraps a pre-built opaque spec object,
  so there is no reference to diff against without an SCCS study.
- **Characterization** `.getDefaultCaseCovariateSettings` — emits 7 `use*`-prefixed keys and a
  stale `fun` attribute (`getDuringCovariateData` vs `getDbDuringCovariateData`). Owned by
  Characterization, not FeatureExtraction; needs its own ground truth.
- **TreatmentPatterns / CohortGenerator** — TreatmentPatterns emits 12 keys with no
  counterpart and has a cross-kernel divergence (`windowEnd` in R only); CohortGenerator's
  real contract lives in an uninstalled Strategus module wrapper and could not be verified.
- **A systematic sweep of every emitted object** against `names()` of its package
  counterpart. This is the durable fix for the whole defect class and should follow; it is
  open-ended (several objects have no reference fixture) and would block the verified work.
- **`plugins/notebook/README.md` is stale** — it documents the plugin as a React component
  with `.tsx` examples, while the source is Vue 3 SFCs. Unrelated to this feature; noted so
  it is not mistaken for something this change introduced.
